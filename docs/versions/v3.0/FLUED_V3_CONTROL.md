# FLUED v3 Control-Manifold Design

This document records two candidate ways to merge Mapping-Network-style ideas
into FLUED v3. Both versions keep the same high-level FLUED direction:

```text
FLUED-v3 = streaming byte-to-latent transducer
         + active segment high-resolution encoding
         + committed history memory
         + explicit prefill/generation semantics
```

The open question is how to control boundary commit, compression budget,
history retrieval, and memory writing without making training even harder than
v2.

## Current Motivation

FLUED v2 already has denoising reconstruction and stable E1 results, but the
training problem remains over-coupled:

```text
reconstruction
denoising
compression density
type boundary priors
downstream BPB
long-context efficiency
```

The observed problem is not "denoising is absent". Denoising is present and
works. The problem is that higher denoising tends to preserve more units, and
the compression controller does not reliably translate target compression into
actual useful downstream compression.

The v3 control idea is:

```text
Do not let arbitrary high-dimensional hidden states directly control boundary,
memory retrieval, and memory writing. Project runtime statistics into a lower
dimensional control space, then make control decisions there.
```

High-dimensional representations still carry content. Low-dimensional control
coordinates decide runtime behavior.

```text
high-dimensional memory slots = content payload
low-dimensional control z     = how to cut, read, write, and spend budget
```

## Shared v3 Runtime Semantics

### Prefill

During prompt prefill, text is known. The active segment may use bidirectional
encoding.

```text
prompt bytes
  -> dynamic semantic segments
  -> active segment encoder, bidirectional
  -> H_seg
       -> Z_seg for backbone / latent stream
       -> memory update for future segments
```

The conceptual path is "segment -> latent -> memory", but the efficient
implementation should use one shared encoder pass and branch from `H_seg`:

```text
H_seg
  -> LatentProjector   -> Z_seg
  -> MemoryCompressor -> delta_M
```

This avoids re-encoding or copying the segment.

### Generation

During generation, the current active segment cannot see future bytes.

```text
generated prefix
  -> active segment encoder, causal
  -> committed memory is visible
  -> predict next byte / next latent
  -> append generated byte
```

The active segment may be revised while it remains active. Once committed, its
high-resolution state is released or moved to compressed memory.

```text
active segment: high resolution, mutable
committed memory: compressed, queryable, frozen unless explicit revision is added
```

## Version A: Learnable Mapping Controller

This was the first, more aggressive fusion idea.

```text
active hidden
+ surprisal statistics
+ reconstruction residual
+ memory query result
+ budget state
+ mode embedding
        |
        v
Mapping Controller
        |
        v
control z
        |
        v
generate or modulate boundary / compression / memory parameters
```

### Intended Use

The controller does not replace FLUED's encoder, decoder, or backbone. It only
controls runtime policy:

```text
BoundaryCommitter:
  threshold, temperature, gate bias, local budget

MemoryCompressor:
  low-rank delta or slot allocation policy

MemoryUpdater:
  write gate, overwrite gate, retention score
```

The strongest allowable parameter modulation is low-rank:

```text
W_i = W_0 + A diag(r_i) B
```

where `r_i` is generated from the segment control vector.

### Why It Is Attractive

- It can adapt boundary and memory behavior to text difficulty.
- It can use different behavior for code, math, CJK, normal prose, and OCR-like
  noisy text without hard-coded rules.
- It gives one place to inject ByteFlow-style information cost, SOMBRERO-style
  boundary enrichment, and FLEXITOKENS-style adaptive compression.

### Hidden Problems

The learnable controller is powerful enough to become a black-box hyperparameter
machine:

```text
old problem: manually tune threshold/compression loss
new problem: controller silently learns unstable thresholds/compression policy
```

Risks:

- It may hide rather than solve compression instability.
- Segment-level dynamic parameters can invalidate cache semantics.
- If `z` changes byte-by-byte, generation latency and reproducibility suffer.
- If trained mostly by reconstruction, it may improve E1 while hurting E3.
- If allowed to generate large weights, it becomes a hypernetwork and makes the
  paper harder to defend.

### Status

Keep Version A as a future extension. Do not make it the first v3 experiment.

## Version B: Frozen Mapping Control

This is the revised and recommended version.

Instead of training a large Mapping Controller, v3 uses a fixed orthogonal or
fixed random-feature projection from runtime statistics into a low-dimensional
control manifold.

```text
runtime state s
  -> fixed projection Phi
  -> low-dimensional z
  -> small/simple control heads
```

Only the small heads or thresholds may be trainable. The main projection is
fixed.

```text
z_t = Phi_fixed(s_t)
p_commit = sigmoid(a^T z_t + beta)
memory_read_weight = softmax(z_t^T z_i)
slot_budget = f_budget(z_t, budget_state)
```

### What Goes Into `s_t`

`s_t` should not be only `mean(hidden)`. It should include explicit runtime
signals:

```text
active hidden mean / variance
delta hidden norm
next-byte surprisal or proxy residual
reconstruction residual
memory hit score
active segment length
current global budget pressure
mode: prefill or generation
byte-type summary
```

### Control vs Payload

This distinction is mandatory:

```text
low-dimensional z:
  decides where to cut, where to read, how much to write

high-dimensional memory slots:
  preserve names, numbers, code, entities, and detailed local content
```

If `z` is forced to carry detailed content, v3 will lose the exact information
that byte-level modeling is supposed to protect.

### Why Version B Fits FLUED Better

FLUED's current hard part is not representational capacity. The 328M v2 model
has enough capacity to reconstruct. The hard part is control:

```text
when to commit a segment
how much compression to allow
which historical segment to query
how much memory to write
how to keep prefill and generation aligned
```

Version B reduces the controller's freedom and makes the hypothesis easier to
test:

```text
Effective runtime control variables live on a lower-dimensional manifold than
the full hidden state.
```

### Main Losses

The fixed projection itself is not trained. Training or evaluation should
regularize behavior:

```text
L_next_byte:
  generation-style main objective

L_recon:
  prefill reconstruction auxiliary objective

L_budget:
  global compression budget, not a fixed per-segment target

L_enrich:
  boundary enrichment near high surprisal / residual / memory miss

L_smooth:
  z trajectory should be smooth inside a segment

L_stability:
  small input perturbations should not collapse boundary/memory behavior
```

## First 5080 Experiment Plan

Do not implement full v3 first. The first experiment should be small and cheap:

```text
FLUED-v2-small + boundary/control probes
```

Goal:

```text
Does a low-dimensional fixed control space produce boundaries that are more
controllable and more aligned with prediction difficulty than the current
boundary head?
```

### Model Size

Use local RTX 5080 with smaller parameters:

```text
d_model=256
num_layers=4
nhead=4
dim_feedforward=1024
seq_len=128
batch_size=16
max_steps=2000 to 5000
```

This is not for final results. It is for fast signal.

### Experiment Matrix

```text
A. v2-small baseline
   current boundary_head, denoise_prob=0.7

B. v2-small low denoise
   current boundary_head, denoise_prob=0.3

C. v2-small high denoise
   current boundary_head, denoise_prob=0.9

D. v2-small budget stress
   compression_weight=0.25, target_compression=0.3

E. FMC probe on saved checkpoints
   fixed projection control diagnostics, no model training changes
```

Run A-D first to produce small checkpoints and logs. Then run the FMC probe on
the latest checkpoints to compare:

```text
m/n controllability
boundary enrichment
boundary density vs residual
seed stability
type boundary behavior
```

### Pass / Fail Interpretation

Good sign:

```text
FMC probe boundaries have higher enrichment and more stable density than the
native boundary head at the same approximate m/n.
```

Bad sign:

```text
FMC only tracks punctuation/byte type, or improves reconstruction diagnostics
without improving next-byte/proxy difficulty alignment.
```

Only after the FMC probe shows signal should we modify `flued/model.py`.

## Next Step: Causal Proxy FMC

The next experiment should answer one question:

```text
Can FMC still beat native boundary when the control inputs are available during
real prefill/generation, without using oracle reconstruction residual?
```

### Why This Is The Next Step

The v3 hypothesis is not "residual is useful". That is obvious. The hypothesis
is:

```text
The control variables needed for boundary/memory/compression decisions can be
captured by a small, stable set of causal or prefill-available proxy signals.
```

If the result only works with `residual_ce`, it cannot become a real runtime
controller. If it works with causal proxies, then FMC is a real design path.

### Candidate Proxy Signals

Use only signals that are available at the relevant runtime:

```text
prefill-available:
  bidirectional hidden drift
  local byte transition statistics
  memory hit / retrieval score
  active segment length
  byte-type summary
  compressed reconstruction residual from already-known prompt

generation-available:
  past next-byte surprisal
  causal byte-LM entropy
  causal hidden drift
  memory hit / retrieval score
  active segment length
  budget pressure
  previous commit distance
```

For the immediate small experiment, use a cheap causal proxy set:

```text
1. previous-position CE residual, shifted right by one
2. causal local byte transition magnitude
3. native boundary probability
4. active position / segment length proxy
5. rolling residual mean over past positions
```

This is still not a perfect generation proxy, but it removes direct target
leakage from the same position.

Better later proxy:

```text
small causal byte LM entropy
```

That is closer to BLT/SOMBRERO and can be computed without knowing the future.

### Experiment Matrix

Run on the existing small checkpoints first, without retraining:

```text
P0 native:
  current boundary_probs

P1 oracle FMC:
  fixed projection using same-position residual_ce

P2 shifted FMC:
  fixed projection using residual_ce shifted from previous positions only

P3 no-residual FMC:
  fixed projection using native bp + byte transition + position + rolling stats

P4 causal-byteLM FMC:
  fixed projection using entropy from a small causal byte LM
```

Metrics:

```text
score-residual correlation
top-k residual enrichment
density stability
type boundary behavior
seed stability
future E3/BPB once model-integrated
```

### Decision Criteria

Strong positive:

```text
P2/P3/P4 still beat native boundary by a large margin on enrichment/correlation.
```

Interpretation:

```text
FMC does not require oracle residual. Move to model-integrated FMC Boundary.
```

Weak positive:

```text
Only P2 works, P3 fails.
```

Interpretation:

```text
The key signal is causal local difficulty. Add a cheap causal byte-LM entropy
or shifted residual predictor before integrating FMC into the model.
```

Negative:

```text
Only oracle P1 works; P2/P3/P4 collapse to native or worse.
```

Interpretation:

```text
FMC as currently defined is mostly exploiting post-hoc residual. Do not add it
to model code. Return to boundary objective design, likely ByteFlow/SOMBRERO
style surprisal or coding-rate supervision.
```

Ambiguous:

```text
FMC improves enrichment but not density stability, or only works on one run.
```

Interpretation:

```text
Run longer small training and at least 3 seeds before touching large models.
```

## If Causal Proxy FMC Works

Implement the smallest model change:

```text
FLUED-v2-small + FMC Boundary
```

Do not implement memory compressor or v3 streaming memory yet.

Minimal model integration:

```text
native hidden/delta
+ causal proxy features
+ fixed projection Phi
+ small boundary head on z
-> boundary_probs
```

Compare:

```text
A. native boundary_head
B. FMC boundary, no new losses
C. FMC boundary + smoothness
D. FMC boundary + enrichment
E. FMC boundary + global budget
```

Main checks:

```text
1. Does m/n become more controllable?
2. Does boundary enrichment improve?
3. Does E1 reconstruction remain stable?
4. Does small E3 BPB improve?
5. Does it generalize across seeds?
```

Only after this works should memory retrieval/control be added.

## If Causal Proxy FMC Fails

Do not continue adding controller complexity.

Fallback plan:

```text
1. Keep FMC only as an analysis tool.
2. Build a direct boundary-quality objective:
   - surprisal enrichment
   - coding-rate reduction
   - memory-hit failure
3. Revisit ByteFlow/SOMBRERO-style losses.
4. Keep v3 memory hierarchy idea separate from FMC.
```

In that case, the v3 focus should shift from:

```text
control manifold
```

to:

```text
better training signal for boundary placement
```

Interpretation:

```text

This supports a narrower v3 hypothesis:

  boundary control should not directly consume same-position residual;
  it should consume a causal learned surprise estimate.

The result does not yet prove the full memory-matrix v3 architecture.
It only proves that a useful control signal can be estimated without future

```

Current best explanation:

```text
FLUED-v2's native boundary head is learning segmentation mostly from local
hidden deltas and compression pressure. It is not directly optimized to mark
positions where the decoder/backbone will be surprised.

The causal surprise probe learns a different variable:

  "given the past bytes, how hard is the current position likely to be?"

That variable is closer to the missing boundary-control signal.
```

Risk:

```text
This is still an offline probe.

It predicts the residual produced by an already-trained FLUED checkpoint.
It has not yet been inserted into training, so it may become unstable if the
target residual distribution moves while FLUED learns.
```

Next implementation experiment:

```text
FLUED-small + auxiliary causal surprise head

Training:
  surprise_head sees causal-shifted bytes or causal hidden states
  surprise_target = stopgrad(reconstruction residual)
  boundary regularizer encourages boundary_probs to enrich high surprise

Important:
  stop gradient through surprise_target
  warm up FLUED reconstruction first
  introduce boundary regularizer gradually
  keep it small; do not add memory matrix yet
```

Decision criteria:

```text
Good:
  m/n becomes more controllable
  boundary-residual enrichment improves
  reconstruction stays stable
  small E3 BPB improves or at least does not degrade

Bad:
  reconstruction drops
  m/n still ignores target
  boundary collapses to uniform high or low probability
  surprise loss dominates reconstruction

If good:
  keep the causal surprise head as a v2.5/v3 bridge.

If bad:
  keep the probe as analysis only and move to direct coding-rate objectives.
```

## Revised v3 Direction

The first FMC idea was too broad:

```text
fixed low-dimensional controller -> boundary/memory behavior
```

The experiments narrow it to:

```text
causal surprise estimate -> boundary placement assistance
```

In plain terms:

```text
FLUED should not ask the boundary head to discover every useful boundary
signal indirectly from reconstruction and compression losses.

It should expose one extra causal variable:

  "How surprising / hard is the current byte or local segment given the past?"

Then boundary training can place semantic cuts where the model expects the
next representation to become hard, unstable, or information-dense.
```

This is still compatible with the future segment-memory v3 design, but it is
a smaller and more testable bridge:

```text
v2:
  reconstruction + compression -> boundary_head

v2.5:
  reconstruction + compression + causal surprise auxiliary -> boundary_head

v3:
  segment latent + causal surprise + committed memory -> streaming transducer
```

## 2026-06-26 Revised Training Direction

The next correction is not to add more architecture. It is to fix the training
signals and evaluation surface.

Core hypothesis:

```text
FLUED is a differentiable byte-to-latent semantic compressor.
It should learn where information density is high, spend more latent budget
there, and compress predictable regions more aggressively.
```

This implies four constraints:

```text
1. Keep soft segmentation.
   Boundary supervision must not become hard top-k tokenization.

2. Do not use fixed per-sample compression as the main objective.
   Average budget can be constrained, but individual samples should adapt.

3. Reconstruction remains a floor, not the only target.
   Clean reconstruction proves information preservation, but not language
   usefulness.

4. Evaluation must include ROI heatmaps.
   Boundary behavior has to be inspected visually across text types, not only
   inferred from scalar metrics.
```

Implemented experimental changes:

```text
tools/analysis/v3_0/train_surprise_assisted_e1.py

New task mixture:
  clean reconstruction
  denoising reconstruction
  future-mask prefix reconstruction

Default denoising schedule:
  denoise_prob  = 0.5
  denoise_steps = 20000

Meaning:
  denoising is an early anti-copying scaffold, not the final objective.
```

Future-mask task:

```text
input:
  prefix bytes visible
  suffix bytes replaced by MASK_ID

loss:
  only visible prefix positions are reconstructed

purpose:
  test whether FLUED can form boundaries when future bytes are unavailable,
  without turning the task into next-byte prediction.
```

Boundary coupling:

```text
old:
  -corr(boundary_probs, surprise_signal)

new default:
  soft ranking loss

meaning:
  high-surprise regions should have relatively higher boundary probability
  than low-surprise regions.

important:
  this is not hard segmentation supervision.
  boundary_probs remain continuous.
```

Coding-rate diagnostics:

```text

  mean(boundary_probs)

rate_boundary_entropy:
  entropy(boundary_probs), exposes 0.52 narrow-band collapse

rate_latent:
  logdet coding-rate proxy on low-dimensional projected z
```

For now coding rate is a diagnostic and weak future constraint candidate. It
does not replace reconstruction and should not become another fixed
target_compression.

Evaluation expansion:

```text

tools/analysis/v3_0/analyze_surprise_metrics.py
```

The ROI heatmap script covers:

```text

digits / formula-like text

repeated template text
entity-heavy text
```

Each scenario exports:

```text

hard spans at threshold 0.5
per-byte-type boundary statistics
summary.json
```

New final eval metrics include:

```text

```

This prevents clean reconstruction accuracy from hiding denoising or
future-mask failures.

Next validation route:

```text

   Confirm no NaN, no boundary narrow-band collapse, and useful ROI heatmaps.
```

## 2026-06-28 Gated Active-Memory Prototype


New switches:

```text

--controller-memory-mode features
```

Design:

```text
Old raw active_memory:
  decoder input = concat(active_state, memory_state)
  controller input = concat(h_t, active_state, memory_state, h_t-active_state, budget)

New gated active-memory:
  decoder input = active_state + gate(active_state, memory_state) * adapter(active_state, memory_state)

    active-memory delta norm
    memory norm
    active norm
```

```text
only compact memory-match signals.
```

## 2026-06-29 seq_len=512 Speed Bottleneck and Low-Risk Optimizations

Problem:

```text
The first seq_len=512 run was abnormally slow:
  batch=8
  GPU utilization ~= 17-26%
  memory used ~= 4GB

The bottleneck is not VRAM.
```

Root cause:

```text
V3CommitControllerSmall.forward has a Python loop over seq_len:

  for t in range(seq_len):
    controller
    active_update
    memory_update
    soft write

At seq_len=512 this creates many small sequential operations and GPU kernels.
The recurrent active/memory dependency prevents simple full parallelization.
```

Implemented low-risk switches:

```text
--update-cell gru|mlp
--commit-stride N
--torch-compile
```

Meaning:

```text
update_cell=mlp:
  replace GRUCell state updates with a smaller MLP state update.

commit_stride=N:
  run the commit controller once every N bytes and reuse the last commit
  probability between controller updates.

torch_compile:
  attempt torch.compile; automatically skips if Triton is unavailable.
```

Benchmark, seq_len=512, d_model=384, hidden=384, controller_hidden=512:

```text
variant          batch  sec/step
gru stride=1     32     2.764
mlp stride=1     32     2.891
gru stride=4     32     1.594
mlp stride=4     32     1.707
gru stride=8     32     1.389
gru stride=16    32     1.277
gru stride=4     64     1.666
gru stride=8     64     1.437
```

Findings:

```text
commit_stride is the useful low-risk speed lever.
MLP update does not improve speed in this implementation.
Increasing batch from 32 to 64 does not help, confirming the sequential loop
is the main bottleneck.
torch.compile is unavailable in this Windows environment because Triton is
missing.
```

Current recommendation for seq_len=512 behavior checks:

```text
Use:
  --update-cell gru
  --commit-stride 8
  --batch-size 32

Why:
  stride=8 is about 2x faster than stride=1 while still updating commit often
  enough for byte-level ROI analysis.

Use stride=16 only for quick smoke tests or if stride=8 remains too slow.
```

Open engineering path:

```text
If seq_len=512/1024 becomes central, the Python recurrent loop needs a deeper
implementation change:
  Triton fused recurrent step, or
  a block-level controller, or
  a chunked active-segment design.

Do not write a CUDA kernel before proving the 512 behavior is worth scaling.
```

Minimal comparison:

```text
A. native boundary
B. native + bigram_surprise regularizer
C. native + learned causal surprise head
D. oracle residual regularizer, upper bound only
```

Decision path:

```text
If learned causal surprise approaches oracle:
  implement a small causal-surprise-assisted boundary head in the small model.

If learned causal surprise only beats bigram slightly:
  keep it as an auxiliary training regularizer, not a runtime controller.

If it fails:
  abandon FMC for now and focus on direct boundary objectives:
  coding-rate reduction, segment stability, memory-hit failure, and
  downstream BPB.
```

## Recommended v3 Name

Use a conservative name:

```text
FLUED-v3-FMC
FMC = Frozen Mapping Control
```

Definition:

```text
FLUED-v3-FMC is a streaming byte-to-latent transducer where boundary commit,
history retrieval, and memory writing are controlled in a low-dimensional
fixed control manifold, while high-dimensional memory slots preserve detailed
content.
```
